# Architecture and data ownership

## Current runtime boundaries

**Existing Python service:** root Dockerfile (python:3.12-slim) runs src/main.py. compose.yml builds that image and passes DEV_SERVER_TOKEN. This is not a Node deployment.

**Node rewrite:** bot-ts/src/main.ts loads environment via process.loadEnvFile(), creates LiveHosts and a discord.js client. At login it registers the nine commands. With intents: [] only interactions/slash commands function; messageCreate remains inert. The Node gateway is not connected to an HTTP health endpoint or a data-review service.

~~~
Discord interactions
    |
bot-ts/src/gateway/{client,commandRouter}
    |
currentCalculatorContext(hosts)
    +---- dataHost -------> data/*.json and data/Locations.csv
    +---- calculatorHost -> damage/bunker handlers
    +---- fuzzyHost ------> aliases and matchers
~~~

**Hot-swap:** PluginHost validates candidate then swaps the in-memory reference. Calculator and fuzzy plugins snapshot compiled dist into dist-hotswap-* to invalidate transitive ESM cache. Data host re-imports entry and rereads files. No code/data cross-host transaction or permanent artifact pinning is implemented.

## Data and control-plane ownership

| Asset | Purpose | Primary protection |
|---|---|---|
| data/Weapons.json, Targets.json, Damage.json, Bunker_piece.json | Calculator source of truth | Git review; regression fixtures; backup before edits |
| data/Locations.csv | Human-curated static aliases (hex, name, type) | Human review, no direct dynamic-war auto-deletes |
| test/fixtures/*.json | Ground truth generated by current Python implementation | Python generator + CI drift check |
| bot-ts/dist | Compiled code for running Node | Rebuild/test; immutable release preferred |
| bot-ts/dist-hotswap-* | Live old and new module graphs | Retain until process shutdown |
| bot-ts/.env and service environment | Tokens and trusted-operator IDs | Private files, OS permissions, no Git |
| error_log.txt and stdout/stderr | Operational logs, potentially user queries | Access limits, retention policy, no public upload |
| Full Foxhole PAK files | Steam-acquired proprietary game content | Private isolated extraction volume, never Git |
| Full map JSON snapshots | Future analytical source, potentially large | Private Zstd archive, immutable manifests, separate backups |
| Derived candidate location tables | Review proposals only | Record source provenance, confidence and human approval |

**Do not conflate**: successful Steam download, successful CUE4Parse export, complete actor/property coverage, correct relic classification, and approved deployment are five separate gates. PR #39 currently only stages acquisition/processed archive; issue #40 covers raw full-fidelity output; #13 resolves permanent/static vs dynamic source.

## Change authority and failure domains

- Repository merges change source, **not** production deployment.
- A running Node process needs restart for external npm dependency changes; code hot-swap cannot safely replace node_modules.
- Guild administrators are not bot-global operators: admin commands require separate user/guild allowlists.
- GitHub PR tests do not prove Discord API behavior, Steam Guard persistence, game export fidelity or backup restore.
- No implemented HA leader/fencing; do not start two independent production bot instances with the same token.
